## 01:30 — 角色门禁单向锁方案完成

**背景**：v65 在 pre_edit_file.js / pre_bash.js 中加入角色门禁，但 trigger 依赖 `.claude/.gate/role.json`（保护区目录），修改需 audit 流程，形成死结。

**排查路径**：
1. 方案 A（豁免 role.json）→ 审计模型驳回：AI 能随意改写 role.json 等于没有门禁
2. 方案 B（人手动管理 role.json）→ 用户否决：输入"顾问/执行"已定义窗口，Hook 必须自动响应
3. 方案 C（单向锁）→ 通过：默认 executor，AI 可写 role.json 锁成 advisor，但 advisor 下门禁拦截一切写入（含 role.json），无法自行解锁

**根因**：豁免方案让 AI 拥有 role.json 的读写自由，三权分立被瓦解。单向锁利用"写入时角色尚未切换"的时序窗口实现：executor → advisor 写入放行，advisor → executor 写入被门禁拦截。

**修复**：
- `CLAUDE.md`：顾问/执行角色增加步骤 0 写 role.json
- `.claude/role.json`：新建，替代 `.claude/.gate/role.json`
- `pre_edit_file.js`：路径改为 `.claude/role.json`，删除 isRoleFileTarget 豁免
- `pre_bash.js`：同上

**教训**：Hook 门禁设计时，豁免判断本身就是最危险的攻击面。正确的门禁不需要任何豁免——利用状态转移的时序窗口（写入前角色为 executor，写入后立即生效）即可实现单向控制。

## 02:30 — 角色门禁 task 目录豁免：修复 advisor 无法写协议文件的回归

**现象**：v67 回退 isRoleFileTarget 豁免后，角色门禁变为无差别拦截。advisor 尝试写 recommendation.md 时被 Hook 拦截——CLAUDE.md 要求顾问写协议文件，但技术手段阻止了它。

**排查路径**：
1. 确认 grep isRoleFileTarget → 零匹配，豁免确实已删除
2. 审查角色门禁逻辑 → L27 对 advisor 无差别拦截所有文件，无任何例外
3. 确认 `.claude/task/` 不在保护区清单中 → 门禁拦截纯粹来自角色判断，不是文件保护

**根因**：v67 "一刀切删除豁免"过度修正。isRoleFileTarget（豁免 role.json 自身）应该删除，但没有补上 task 目录豁免。advisor 的协议职责（写 direction / recommendation）需要写入 `.claude/task/`，而这些文件不是业务代码、不影响三权分立。

**修复**：
- `pre_edit_file.js`：角色门禁增加 `isTaskFile = filePath.includes(".claude/task/")`，task 文件跳过拦截
- `pre_bash.js`：同上逻辑，从 command 提取路径后判断是否全部在 task 目录

**教训**：删除豁免时区分"危险豁免"和"必要豁免"。role.json 豁免危险（可自我解锁），task 目录豁免安全（只能写协议文件，无法提权）。一刀切会误伤合法操作。Commits: v1-20260529-69。

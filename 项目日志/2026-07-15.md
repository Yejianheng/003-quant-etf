## 20:45 — 513100 纳指 7/14 收盘价数据错误

**现象**：用户反馈纳指 513100 在 7/14 涨了 +0.09%，但 `nav_2026.html` 图表显示策略 Δ% 为 -0.3%，纳指基准线也跌 -0.37%。用户明确指出数据有问题。

**排查路径**：
1. 图表纳指基准线核对 → 基准线也跌 -0.37%，排除策略逻辑问题，确认是源数据错误
2. parquet 数据检查 → `data/513100.parquet` 7/14 close=2.160，7/13 close=2.168，涨跌幅=-0.37%
3. WebSearch 核验 → 腾讯证券/搜狐行情确认 7/14 真实收盘=2.170，涨跌幅 +0.09%
4. 回溯数据来源 → outcome.md 记录显示 v211 session 在 **09:31**（开盘 1 分钟）跑了 `nav_chart.py`，图表脚本的 `update_all_etfs()` 调 `update_single_etf()` 拉取数据，腾讯 API 返回盘中不完整日线（513100 volume=87,842 vs 正常 ~2.86 亿），`update_single_etf` 无校验直接 `pd.concat` 入库
5. 510300 同日也中招 → close=4.745→4.837（差 +1.96%），volume 同样异常（165,525 vs 正常 ~18 亿）
6. 时间线确认 → 坏数据在 commit `6d98405 v211-20260714-2`（11:13）中已入库；当晚 22:32 的 `仓位` 命令因 `start_date > end_date` 跳过未覆盖

**根因**：两个缺陷叠加——①`update_single_etf()` 无时间门禁，盘中 09:31 的 API 数据照样接受 ②API 返回什么就存什么，无任何外部核验。腾讯财经在开盘 1 分钟时返回的日线只有 1 分钟成交量，是未完成的数据快照。

**修复**：
- 手动覆写 `data/513100.parquet` 和 `data/510300.parquet` 中 7/14 行，用腾讯财经完整日线数据
- 重跑 `nav_chart.py` 生成正确图表
- 写 direction.md 规划系统性修复：时间门禁（15:00 前不拉当日）+ WebFetch 核验（拉到数据后调搜狐/东方财富行情页交叉验证收盘价）+ 核验不通过阻断图表生成

**教训**：
1. `update_single_etf()` 的增量更新逻辑对 API 返回数据零校验。volume 异常（< 历史均值 1%）应自动告警
2. 盘中任何时段调 API 都可能拿到不完整日线，时间门禁是最简单有效的一刀切
3. API 数据不能直接信——外部网页（搜狐/东方财富行情页）是免费的交叉验证锚点
4. 图表是决策依据，数据错一线则全线错，验证必须是硬门禁不是可选项
5. AI 收到用户反馈数据异常时，应先 WebSearch 核验真实值，再对比 parquet，而不是凭空猜测"数据源延迟"
